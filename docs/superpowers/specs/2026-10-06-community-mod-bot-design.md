# Дизайн: Telegram-бот-модератор для крупных сообществ (SaaS)

Дата: 2026-10-06
Статус: утверждён

## Продукт

Бот-автоматизатор для владельцев Telegram-сообществ (от 5000 участников) — заменяет ручной
труд администрирования чата. Мульти-тенантный SaaS: один код обслуживает тысячи чатов.

### Целевая аудитория

- Владельцы крипто- и трейдинг-сообществ.
- Админы чатов поддержки и брендов.
- Менеджеры платных мастермайндов и закрытых клубов.
- Организаторы локальных сообществ.

### УТП

«Модератор, который настраивается за 3 клика» + точная статистика активности.

## Технический стек

- Язык: Python 3.12+, фреймворк `aiogram 3.x`.
- БД: PostgreSQL (обязательно), ORM `SQLAlchemy 2 async` (`psycopg3`).
- Миграции: `alembic`.
- Конфиг: `pydantic-settings` через env.
- Линт/типы/тесты: `ruff`, `mypy`, `pytest` + `pytest-asyncio`.
- Кэш/очереди/троттлинг: `Redis` (`redis.asyncio`).
- Фоновые задачи: `APScheduler` (AsyncIOScheduler, хранение джобов в БД).
- Деплой: docker-compose (`bot` + `worker` + `redis` + `postgres`). Dev — polling (или
  webhook через туннель), prod — webhook (по флагу конфига).

## Архитектура

Модульный монолит: один бот-процесс обслуживает все чаты; тяжёлый фоновый код вынесен
во второй процесс `worker`.

### Компоненты monorepo `tg_botSaas`

```
bot/
  app.py             # точка входа (polling/webhook по флагу)
  config.py          # env-конфиг (pydantic-settings)
  db/                # SQLAlchemy async engine, сессии
  models.py          # ORM-модели
  modules/
    antispam/        # фильтры: ссылки, капс, повторы, стоп-слова
    greeting/        # приветствие + кнопки-ссылки
    captcha/         # верификация новичков («Я человек»)
    scheduler/       # автопостинг по cron
    stats/           # активность, топ, динамика роста/оттока
  billing/           # тарифы, лимиты, Telegram Stars
  support/           # общие хелперы: права, middleware, rate-limiter, ошибки
migrations/          # alembic
worker/              # процесс: APScheduler (шедулер + агрегация + таймауты капчи)
tests/
docker-compose.yml   # bot + worker + redis + postgres
Makefile              # test / lint / typecheck / dev / seed
```

### Redis

Используется для: глобального троттлинга исходящих запросов к Telegram API
(anti-flood), хранения состояния капча-задач и дедупликации повторяющихся сообщений
(anti-repeat). Redis — источник истины только для эфемерного состояния; всё долговременное
живёт в PostgreSQL.

### Мульти-тенантность

- Единый бот добавляется в каждый чат как администратор (нужны права на удаление сообщений
  и ограничение участников).
- Конфиг каждого чата — запись `Chat` (настройки как `jsonb`), тариф.

### Онбординг чата (подключение бота)

- Инструкция для админа встроена в флоу подключения: бот требует **выключенный Privacy Mode**
  (@BotFather → Settings → Group Privacy → Off), иначе не видит сообщения участников и
  антиспам/статистика не работают. Бот проверяет доступность и предупреждает.
- При добавлении в существующий чат бот делает первичный запрос `getChat` → `member_count`
  (события `chat_member` для уже сидящих участников Telegram не присылает) и сохраняет
  в `Chat.member_count`.

### Модели БД (ядро)

- `Chat` — chat_id, настройки `jsonb`, `plan`, `member_count`, `branding_flag`.
- `Moderator` — админы, подключившие/управляющие ботом (chat_id ↔ user_id).
- `Member` — участник в чате: user_id, warn_count, joined_at, left_at.
- `MessageLog` — лог срабатываний фильтров: user_id, тип фильтра, результат, время.
  Текст сообщения не храним (меньше персональных данных и объёма).
- `ChatMemberEvents` — события enter/leave для статистики.
- `DailyStats` — агрегаты по дням на чат.
- `CaptchaChallenge` — активные капча-задачи (chat, user, expires_at).
- `ScheduledTask` — задачи автопостинга: cron, текст, chat_id.
- `PaidPlan` — платежи/подписки: chat_id, plan, starts_at, expires_at.
- `ErrorLog` — залогированные исключения.

### Масштабирование БД

- **Партиционирование**: `MessageLog` и `ChatMemberEvents` — партиционирование по месяцам
  (`RANGE (created_at)`, `declarative`-партиции в SQLAlchemy/Alembic + автосоздание новых
  партиций на старте worker'а). Без этого агрегации статистики убьют производительность
  через полгода.
- **Индексы** (составные, обязательные):
  - `MessageLog(chat_id, created_at)`;
  - `Member(chat_id, user_id)`;
  - `ChatMemberEvents(chat_id, created_at)`;
  - `DailyStats(chat_id, day) unique`.
- Функции агрегации статистики идут только по партиционированным диапазонам дней
  (push-down filtering).

## Функциональные модули

### Анти-спам (`antispam`)

- Правила хранятся в настройках чата (`jsonb`); у каждого правила — поведение:
  `delete` или `delete+warn`.
- Фильтры MVP:
  - ссылки (regex + whitelist разрешённых доменов);
  - КАПС: >70% букв в верхнем регистре и длиннее N символов;
  - повторы: одинаковое сообщение того же юзера за N минут (дедупликация через Redis
    слепок в течение окна, чтобы не хранить в БД текст);
  - стоп-слова: список админа.
- Срабатывание → запись в `MessageLog`, `warn_count+1`, бан после N варнов.
- На бесплатном тарифе действуют только предустановленные базовые фильтры; гибкие правила —
  на `pro`.

### Приветствие (`greeting`)

- Триггер: `chat_member` update (join).
- Текст и кнопки-ссылки — из настроек чата.
- Брендинг-строка «Работает на базе @bot»: флаг `show_branding`;
  на бесплатном тарифе принудительно включён.

### Капча (`captcha`)

Жёсткий флоу (иначе спам-боты пишут в чат до решения капчи):

1. `chat_member` (`new_chat_member`) → сразу `restrict_chat_member`: запрет на отправку
   сообщений (и других прав) для новичка.
2. Бот постит сообщение с inline-кнопкой «👤 Я человек»; создаётся `CaptchaChallenge`
   (chat, user, `expires_at`).
3. `callback_query` по кнопке → удаляем challenge, `restrict_chat_member` возвращает
   права новичка.
4. По истечении `expires_at` (отслеживает worker по Redis-состоянию + БД) — `restrict`
   навсегда/на время (параметр чата) либо `ban`.

Решение капчи фиксируется **только** по callback — ждать произвольных сообщений новичка
недостаточно, он обязан нажать кнопку.

### Шедулер (`scheduler`)

- `ScheduledTask`: cron-выражение + текст (+ опционально часы/таймзона).
- `worker` раз в минуту выбирает задачи, чей cron совпал, и отправляет сообщение в чат.
- Доступен на `pro`.

### Статистика (`stats`)

- Источники: `MessageLog` (счётчики), `ChatMemberEvents` (join/leave).
- `worker` раз в час аггрегирует в `DailyStats`: уникальные активные за день, новые,
  ушедшие, суммарная активность.
- Админу через `/stats`: активность за 7 дней, топ-10 участников, динамика роста/оттока.
- Продвинутая статистика — на `pro`; на free — только базовая сводка.

## Тарифы и оплата (`billing`)

### Тарифы

- `free`: до 1000 участников — базовый анти-спам, приветствие, капча, базовая сводка,
  брендинг принудительно. Цель — захват рынка.
- `pro`: свыше 1000 участников, далее платно: продвинутая статистика, гибкие правила,
  шедулер, удаление логов, без брендинга. Стартовая цена $10/мес, выставляется в Stars
  по курсу Telegram (значение цены в Stars — из конфига).
- `enterprise`: на будущее — `pro` без лимитов, кастомный брендинг, API. В MVP только
  фундамент (снятие лимитов).

### Логика

- Команда «Апгрейд» → `sendInvoice` (Telegram Stars).
- `pre_checkout_query` → подтверждение; `successful_payment` → `Chat.plan=pro`,
  запись `PaidPlan` c `expires_at`.
- **Renewal-механика (важно): Telegram Stars НЕ поддерживает автопродление.** За 3 дня
  до `expires_at` worker шлёт админу инвойс с кнопкой «Продлить Pro»; при неоплате к
  `expires_at` тариф понижается до free. Рекуррентного списания нет — продление всегда
  явным действием пользователя.
- Контроль лимитов: при `ChatMembersUpdated` пересчитываем `member_count`; превышение 1000
  на `free` → выключаем расширенный функционал и шлём админу напоминание.

## Обработка ошибок и безопасность

- Middleware-логгер: исключение в handler → запись в `ErrorLog` + alert суперадмину
  (fatal только).
- `TelegramAPIError` retry-able — retry с backoff, процесс не падает.
- Админ-действия идемпотентны (unique-констрейнты в БД).
- Каждый изменяющий хендлер проверяет права через `get_chat_member` (owner/administrator);
  сервисные команды — только `SUPERADMIN_IDS` из env.
- Секреты не пишутся в БД/логи.

### Rate limits / Flood control

- **Исходящие**: глобальный rate-limiter на все отправки в Telegram (aiogram
  throttling middleware поверх Redis-счётчиков на `(chat_id, method)` + глобальный
  бюджет). При массовом входе (например, реклама канала — 1000 приветствий разом) запросы
  ставятся в очередь и уходят по таймингу, а не вбрасываются пачкой → иначе 429 и риск
  бана токена.
- **Входящие**: троттлинг хендлеров (лимиты на сообщения пользователя/чата), чтобы
  антиспам-логика не разрасталась в DoS-бомбардировку.
- `429 Too Many Requests` обрабатывается централизованно: `retry_after` из ответа,
  backoff, очередь.

### Фоновый процесс (worker)

- **APScheduler** (не голый `asyncio.sleep` — ненадёжно при рестартах): AsyncIOScheduler,
  JobStore с хранением состояния джобов в БД/Redis, чтобы расписания переживали рестарты.
- Задачи: шедулер автопостинга, агрегация статистики в `DailyStats` (ежечасно),
  таймауты капча-задач, renewal-уведомления за 3 дня до `expires_at`, автосоздание
  партиций на новый месяц.

## Окружение разработки и тестирование

- docker-compose: `postgres` + `redis`; локально `python -m bot.app --polling`.
- **Webhook локально**: туннель (ngrok / Caddy reverse_proxy) — polling не вскрывает
  реальных проблем с rate limits; в Makefile команда для поднятия туннеля и
  `set_webhook`.
- **`make seed`**: заполнение БД тестовыми чатами с 10 000+ фейковых `MessageLog` /
  `ChatMemberEvents` — проверка пагинации, агрегаций и партиционирования.
- `make test` — pytest (юнит: фильтры антиспама табличными кейсами, cron-матчинг,
  подсчёт статистики; интеграция: хендлеры на мок-сервере Telegram, БД).
- `make lint`, `make typecheck`.

## Объём MVP (что НЕ входит)

- Mini App / веб-панель (архитектура позволяет добавить позже).
- White-label и API-доступ.
- Кастомные прайсы для enterprise.
- Приватные сообщения между участниками, аналитика контента (NLP-разметка текста).
